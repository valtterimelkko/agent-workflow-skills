# Codebook Development Guide

Based on DeCuir-Gunby, Marshall & McCulloch (2011) and best practices for team-based thematic analysis.

## Overview

A codebook is a structured reference guide that ensures consistency in coding, especially for team-based analysis or when using coding reliability approaches.

## When to Use a Codebook

| Approach | When Appropriate |
|----------|------------------|
| **Reflexive TA** | Personal codebook for tracking codes; evolves organically |
| **Codebook TA** | Structured codebook with definitions; some iteration allowed |
| **Coding Reliability TA** | Fixed codebook with strict definitions; reliability testing required |

## Codebook Components

### Essential Elements

| Component | Description | Example |
|-----------|-------------|---------|
| **Code Name** | Concise, descriptive label | "Exercise as stress relief" |
| **Definition** | Clear explanation of what code captures | "References to physical activity as means of managing stress" |
| **Inclusion Criteria** | Specific indicators for applying code | Include: mentions of running, gym, yoga for stress reduction |
| **Exclusion Criteria** | Boundary conditions | Exclude: exercise for weight loss only |
| **Examples** | Representative quotes | "I go running when work gets too overwhelming" |
| **Non-examples** | Borderline cases that don't fit | "I exercise to lose weight before vacation" |

### Optional Elements

- Source (theory-driven vs. data-driven)
- Creation/revision dates
- Related codes
- Notes on application

## Codebook Development Process

### For Theory-Driven Codes (Deductive)

1. **Generate code** from literature, theory, or research questions
2. **Create definition** based on theoretical framework
3. **Provide examples** from pilot data or literature

### For Data-Driven Codes (Inductive)

1. **Read through data** immersively
2. **Create new codes** for emergent patterns
3. **Define codes** based on observed patterns
4. **Provide examples** from actual data

### Iterative Refinement

1. Test codes on subset of data (3-5 transcripts)
2. Adjust definitions as needed
3. Add, merge, or eliminate codes
4. Continue until codebook stabilizes

## Maintaining Consistency

### Individual Coding
- Review codebook before each session
- Keep memo log of coding decisions
- Periodically re-code early data to check consistency

### Team Coding
- Conduct training sessions with practice data
- Calculate inter-rater reliability
- Hold calibration meetings for discrepancies
- Document resolution of disagreements

### Inter-Rater Reliability

| Statistic | Use | Target |
|-----------|-----|--------|
| Percent Agreement | Simple calculation | ≥80% |
| Cohen's Kappa | Two raters, accounts for chance | ≥0.60 |
| Fleiss' Kappa | Three+ raters | ≥0.60 |
| Krippendorff's Alpha | Complex situations | ≥0.67 |

## Common Challenges

### Too Many Codes (Code Explosion)
**Solution:** Group similar codes; aim for 20-35 refined codes

### Definitional Drift
**Solution:** Regular codebook review; re-read definitions frequently

### Overlapping Codes
**Solution:** Clarify boundaries; consider merging

### Vague Definitions
**Solution:** Add specific inclusion/exclusion criteria

## Best Practices

1. **Start small** - Begin with 10-15 provisional codes
2. **Test continuously** - Apply to new data before finalizing
3. **Stay flexible** - Codes will evolve as understanding deepens
4. **Document everything** - Maintain revision log
5. **Balance granularity** - Avoid lumping everything together or splitting too finely

## Time Investment

- Initial codebook development: ~60 hours
- Refinement: Ongoing throughout analysis
- Team training: 2-4 hours per coder
